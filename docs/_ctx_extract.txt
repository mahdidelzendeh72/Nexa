# Final Prompt — Context Management & Context Budget Specification
Context Management & Context Budget Specification
1. Purpose
The Agent Platform MUST provide a production-ready Context Management capability.
Context Management is responsible for determining what information should be available to the LLM for a specific Agent step while respecting the selected model's context-window limitations.
The objective is NOT to send as much information as possible.
The objective is:
> Provide the smallest useful context that contains the information required for the Agent to perform the current task safely, correctly, and effectively.
Context Management MUST be implemented as part of the Agent Runtime architecture.
However, DO NOT reimplement functionality that is already provided by the current Microsoft Agent Framework.
Before implementing custom Context Management functionality:
1. Inspect the currently installed Microsoft Agent Framework packages.
2. Inspect the current APIs.
3. Determine whether Context Providers, Middleware, Harness, Sessions, or other Agent Framework capabilities already solve the requirement.
4. Prefer native Agent Framework capabilities where appropriate.
5. Introduce application-specific abstractions only where the platform needs additional behavior, policy, persistence, observability, or provider independence.
Do NOT invent Microsoft Agent Framework APIs.
---
2. Context Window vs Context Management
The Context Window is a model-level limitation.
For example:
Model Context Window = 128K tokens
The context sent to the model may contain:
System instructions
Developer instructions
Agent instructions
Security policies
User request
Conversation history
Conversation summary
Retrieved memory
RAG / knowledge context
Tool definitions
Tool results
MCP results
Task state
Decision context
Runtime metadata
The application MUST NOT assume that the entire model context window should be consumed.
Instead, the Agent Runtime MUST maintain a configurable application-level Context Budget.
Example:
Model Context Window:
128K
Application Context Budget:
110K
Reserved Budget:
18K
The reserved budget exists for:
Future tool results
Agent output
Additional execution steps
Runtime metadata
Safety margin
The exact values MUST be configurable.

8. Context Priority
Context items SHOULD have a priority.
Recommended levels:
Critical
High
Medium
Low
Default priorities:
Critical:
System instructions
Security policies
Current user request
Mandatory runtime constraints
High:
Relevant tool results
Relevant memory
Active task state
Important decision context
Medium:
Recent conversation
Relevant RAG results
Previous observations
Low:
Old conversation
Historical observations
Superseded tool results
Low-confidence memory
When the context budget is exceeded:
1. Remove irrelevant low-priority information.
2. Compact low-priority information.
3. Summarize where appropriate.
4. Preserve high-priority information.
5. NEVER remove mandatory security instructions or the current user request.

11. Token Estimation
The system SHOULD estimate token usage before sending a request.
Prefer a tokenizer compatible with the selected model when available.
If exact tokenization is unavailable:
Use a conservative approximation.
Mark the estimate as approximate.
Keep an additional safety margin.
The system SHOULD expose:
EstimatedInputTokens
EstimatedOutputTokens
ContextBudget
ReservedTokens
AvailableTokens
ContextUtilization
Do not rely solely on character count when an appropriate tokenizer is available.

RAG answers:
> What does the available knowledge/documentation say?

RAG results MUST be treated as candidate context.

17. Conversation Compaction
When conversation history exceeds its configured budget:
1. Identify important historical information.
2. Create a task-oriented summary.
3. Preserve recent messages.
4. Preserve important unresolved information.
5. Remove redundant historical messages.
6. Recalculate the context budget.
The summary should be useful for continuing the task.
Bad:
"The user discussed hotel search."
Good:
"The user is searching for a refundable hotel in Mashhad for Aug 20-22. Provider A returned no availability. Provider B currently has availability."
---
18. Tool Result Management
Tool Results are temporary execution observations.
They MUST NOT automatically become long-term Memory.
Large Tool Results MUST be compacted.
Example:
Tool Result:
30K tokens
|
v
Result Processing
|
+-- Structured Extraction
+-- Filtering
+-- Important Fields
+-- Summarization if necessary
|
v
Compact Observation:
3K tokens
Prefer deterministic processing when possible.
For structured data, prefer:
Field selection
Filtering
Pagination
Top-N selection
Aggregation
Structured extraction
before using an LLM to summarize the result.

24. Context Trimming
If context remains over budget after compaction:
1. Remove irrelevant old observations.
2. Remove superseded tool results.
3. Remove low-relevance RAG results.
4. Remove low-confidence memories.
5. Compact old conversation.
6. Remove low-priority historical messages.
Never remove:
System instructions
Security policies
Mandatory runtime constraints
Current user request
unless the underlying Agent Framework explicitly manages those elements.
---
25. Context and Task State
Long-running tasks MUST NOT rely on the Context Window as persistent state.
Persistent task state MUST be stored externally.
Example:
Long-Running Task
|
+-- Task State -> Task Store
|
+-- Important Decisions -> Decision Store
|
+-- Long-Term Facts -> Memory
|
+-- Knowledge -> RAG
|
+-- Recent Execution -> Context
The Context Manager retrieves only the relevant Task State required for the current Agent step.

32. Failure Handling
Context Management MUST fail gracefully.
If:
Memory is unavailable
RAG is unavailable
Tokenizer is unavailable
Tool result is too large
MCP result is too large
Context exceeds the configured budget
the system SHOULD attempt graceful degradation.
Preferred sequence:
Full Context
|
v
Compact
|
v
Summarize
|
v
Trim
|
v
Minimal Safe Context
If the request still cannot fit within the model's hard limit, return a controlled error.
Do not blindly send an oversized request.
Memory and RAG failures SHOULD NOT fail the entire Agent execution unless the specific Agent configuration explicitly requires them.

42. Architectural Principles
The implementation MUST follow these principles.
Principle 1 — Context Is Temporary
Context is working memory for an Agent step.
It is not persistent state.
Principle 2 — Relevance Over Volume
More context does not necessarily produce better reasoning.
Prefer:
Relevant 10K tokens
over:
Irrelevant 80K tokens.
Principle 3 — Preserve Critical Information
Security policies, system instructions, mandatory runtime constraints, and the current user request have the highest priority.
Principle 4 — Use Native Framework Capabilities
If Microsoft Agent Framework already provides the required capability, use it instead of implementing a duplicate system.
Principle 5 — Compact Before Trimming
Prefer:
Compact
->
Summarize
->
Trim
over immediately deleting context.
Principle 6 — Externalize Persistent State
Persistent information belongs in:
Memory
Task Store
Decision Store
Knowledge Store
Conversation Store
not in an ever-growing Context Window.
Principle 7 — Provider Independence
Do not couple Context Management to a specific LLM, Memory provider, vector database, or MCP server.
Principle 8 — Observable Context
Developers should be able to understand what information was available to the Agent without accessing private Chain-of-Thought.
Principle 9 — Security Before Relevance
Information must be authorized before it is considered for context injection.
Semantic relevance MUST NOT bypass authorization.
Principle 10 — Incremental Complexity
Build the simplest reliable Context Management system first.
Only introduce advanced ranking, adaptive budgets, semantic compression, or optimization after the basic system is stable and measurable.
